# Архитектура плагина (Nginx-издание)

## Границы ответственности

Установщик предполагает, что Matrix-стек уже работает. Его задача —
надстроить над ним запись звонков и не сломать ничего из существующего.
Отсюда три правила, которые определяют почти все решения в коде:

1. **Не трогать чужое.** Свой nginx-контейнер, свой каталог конфигов, свой
   порт. Интеграция в чужой nginx — отдельный режим с явным подтверждением.
2. **Не падать от неполной конфигурации.** Любой отсутствующий параметр —
   это диагностика в ответе API, а не `KeyError` и не рестарт-цикл.
3. **Ошибка должна называть причину.** Никаких `trap ERR at line N`: код
   возврата, команда, строка, файл, каталог и следующий шаг.

## Почему контроллер не знает про LiveKit

В монолитной версии контроллер читал `LIVEKIT_KEY` из окружения на импорте
модуля. Плагину LiveKit не нужен: запись идёт браузером, Egress не
используется. Жёсткая зависимость приводила к `KeyError` при пустом
окружении и вечному `Restarting`. Здесь `_reconcile()` намеренно пустой, а
все переменные читаются лениво.

## Авторизация

Кнопка отправляет `Authorization: Bearer <matrix access token>`. Контроллер:

1. спрашивает у Synapse `/_matrix/client/v3/account/whoami`, кто это;
2. читает `m.room.power_levels` и `m.room.member` для вызывающего;
3. отказывает, если пользователь не в комнате или power < `RECORDING_MIN_POWER_LEVEL`;
4. при недоступном Synapse отвечает `503` — fail closed.

`powerLevel` из тела запроса игнорируется: он приходит из браузера и
подделывается одной строкой в консоли.

## Почему worker в host network

Chromium должен открыть Element Call на `127.0.0.1:8090`, поэтому worker
работает в сети хоста. Из этого следует:

- порт worker'а проверяется preflight'ом на занятость;
- контроллер обращается к воркерам через `host.docker.internal`
  (`extra_hosts: host-gateway`), а не через `127.0.0.1`;
- `PUBLISH_LOOPBACK_PORTS` управляет публикацией портов контроллера и
  портала, но не воркера.

## Как nginx получает адрес контроллера

Режим `standalone`: адрес резолвится один раз при установке в IP контейнера
на общей docker-сети и записывается в конфиг литералом. Это исключает
рантайм-DNS: nginx резолвит имена один раз при старте, и при пересоздании
контейнера без `--repair` получается 502 «на ровном месте». `--repair`
перегенерирует конфиг с актуальным IP.

Режим `external`: то же самое, но конфиг кладётся в каталог конфигов фронта,
а адрес — `127.0.0.1` плюс опубликованный порт.

## Структура файлов nginx

```
<plugin>/nginx/conf.d/
├── 00-recorder-plugin.conf          только server{} — безопасно в conf.d
└── includes/
    └── recorder.locations.inc        только location — только через include
```

Файл с `location` в `conf.d/` разбирается в контексте `http{}` и даёт
`"location" directive is not allowed here`. Это самая частая причина
нерабочих попыток; в тестах есть negative-тест, который падает, если кто-то
вернёт такое размещение.

## Идемпотентность

Повторный `--install` и `--repair`:

- пересоздают контейнер только при расхождении монтирований или портов;
- перегенерируют конфиги целиком, а не дописывают;
- вставку `include` во фронт-конфиг делают один раз (проверка перед вставкой);
- сохраняют прежний `RECORDER_TOKEN`, чтобы запущенные воркеры не потеряли
  доступ.

## Откат

Перед правкой чужого конфига создаётся `.bak.<timestamp>`. Если `nginx -t`
после правки не проходит — файл восстанавливается из бэкапа, nginx
перезагружается со старым конфигом, а установщик завершается с ошибкой, в
которой напечатан вывод `nginx -t` (stdout и stderr раздельно).
